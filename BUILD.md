# Pict — BUILD.md

Every decision baked in before implementation. This is the source of truth for *how* Pict is built; `pict-prd.md` remains the source of truth for *what* it does. Where the two disagree, this file records the resolution.

- **Stack:** React + Vite + TypeScript, PWA via `vite-plugin-pwa` (`injectManifest`), Cloudflare Pages + Functions + D1, a separate scheduled Cloudflare Worker for the daily cron, Claude Haiku (`claude-haiku-4-5-20251001`) for suggestions, Cloudflare Access in front of everything.
- **Single user.** No login UI, no multi-tenancy, no per-user rows. Lists are labels (`me` / `us` / `family`) on one account.
- **Light theme only. Oxblood `#8C3A46` is the only chrome colour.** Artwork carries the mood.

---

## 0. The three resolutions (do these decisions govern the build)

### 0.1 Critic scores — **kept OMDb→RT as primary, TMDB `vote_average` as fallback, gate renamed "Critic score"**

**Verified (July 2026):** OMDb's free tier (1,000 req/day) still returns Rotten Tomatoes in the `Ratings` array as `{ "Source": "Rotten Tomatoes", "Value": "94%" }`. So RT is technically available.

**But** coverage is unreliable in exactly the cases this library hits: TV series frequently return `N/A`, and newer / regional titles (Irish/RTÉ content, small releases) often have no RT entry at all. Making RT the *sole* gate would silently drop good candidates.

**Decision — a single unified "Critic score" gate:**
- Query OMDb by **IMDb ID** (far more reliable than by title). Parse the `Ratings` array for `Source == "Rotten Tomatoes"`, strip `%` → integer `rt_score`.
- If RT is missing / `N/A` / OMDb errors, or the title is TV, fall back to **TMDB `vote_average × 10`** (a 0–100 scale).
- Persist both on the title row: `rt_score` (nullable, the real RT number when we have it) and `critic_score` (the resolved value actually used for filtering, never null). The Discover gate always filters on `critic_score`.
- **The setting is called "Critic score" everywhere** — UI, code, comments. The mockup already labels the slider *"Critic score floor"*, so this is consistent with the design, not a departure from it. The `ScoreBadge` shows `rt_score` with an RT-red dot when present, otherwise `critic_score` with a neutral dot (badge component branches on source).

**Why this way:** RT via OMDb is real but too sparse to trust alone for a library that includes TV and Irish content. A resolved `critic_score` that prefers RT and degrades gracefully to TMDB gives one dependable number to gate on, while still surfacing the genuine RT score when it exists.

### 0.2 Abandoned shows — **excluded from the taste profile entirely**

Abandonment is a noisy signal: a show gets dropped for length, timing, or mood as often as for genuine dislike, so treating it as a *negative* would push the model away from whole genres you actually enjoy. Excluding abandoned titles keeps the profile built only from confident positives (finished, or fully-caught-up in-progress), which is what "these are my tastes" should mean. Implemented in `shared/haiku.ts`'s eligibility query: `state IN ('completed')` for film, and completed-or-caught-up for TV; `abandoned` rows never enter the profile and are only used to exclude the title from candidate discovery (so we never re-suggest something you dropped).

### 0.3 Quiet hours — **premature; not built in v1, with a marked extension point**

The cron fires once per day at 08:00 Europe/Dublin — a civilised hour by construction — and there is exactly one recipient who controls their own device DND. Building configurable quiet-hours windows, timezone drift handling, and re-queue logic buys nothing over "the one daily batch lands at 08:00." Skipped for v1. A stub `withinQuietHours(now): boolean` lives in `worker/src/index.ts` returning `false`, called at the top of the send loop, with a comment marking exactly where a real implementation (and its `settings` columns) would slot in.

### 2.1 Migration file naming

### 2.2 `migrations/0001_init.sql`

```sql
-- A tracked show or film. One row per TMDB title, shared across audiences.
CREATE TABLE titles (
  id            INTEGER PRIMARY KEY,
  tmdb_id       INTEGER NOT NULL,
  imdb_id       TEXT,                 -- from TMDB external_ids; keys OMDb lookups
  media_type    TEXT NOT NULL,        -- 'tv' | 'movie'
  name          TEXT NOT NULL,
  overview      TEXT,
  poster_path   TEXT,
  backdrop_path TEXT,
  art_palette   TEXT,                 -- JSON {base,a,b,c,tint} (§4.4)
  first_air     TEXT,                 -- first_air_date | release_date (ISO)
  runtime       INTEGER,              -- minutes (movie) or episode avg (tv)
  genres        TEXT,                 -- JSON string[] of TMDB genre names
  networks      TEXT,                 -- JSON string[] (tv networks / movie studios)
  tmdb_vote     REAL,                 -- TMDB vote_average (0–10)
  rt_score      INTEGER,              -- Rotten Tomatoes % from OMDb, or NULL
  critic_score  INTEGER NOT NULL,     -- resolved gate value 0–100 (§0.1)
  rt_checked_at TEXT,                 -- last OMDb fetch (ISO); throttles re-checks
  created_at    TEXT NOT NULL,
  UNIQUE(tmdb_id, media_type)
);

-- My relationship to a title. Multiple audiences can track the same title.
CREATE TABLE entries (
  id            INTEGER PRIMARY KEY,
  title_id      INTEGER NOT NULL REFERENCES titles(id) ON DELETE CASCADE,
  audience      TEXT NOT NULL,        -- 'me' | 'us' | 'family'
  state         TEXT NOT NULL,        -- 'saved' | 'watching' | 'completed' | 'abandoned'
  notify        INTEGER NOT NULL DEFAULT 1,
  added_at      TEXT NOT NULL,
  updated_at    TEXT NOT NULL,
  UNIQUE(title_id, audience)          -- one entry per title per audience
);

-- Episode-level progress (TV only).
CREATE TABLE episodes (
  id            INTEGER PRIMARY KEY,
  title_id      INTEGER NOT NULL REFERENCES titles(id) ON DELETE CASCADE,
  season        INTEGER NOT NULL,
  number        INTEGER NOT NULL,
  name          TEXT,
  air_date      TEXT,                 -- ISO date
  watched_at    TEXT,                 -- NULL = unwatched
  notified_at   TEXT,                 -- NULL = not yet pushed  (ADDED vs PRD §3)
  UNIQUE(title_id, season, number)
);

-- Streaming availability (films). Region IE.
CREATE TABLE releases (
  id            INTEGER PRIMARY KEY,
  title_id      INTEGER NOT NULL REFERENCES titles(id) ON DELETE CASCADE,
  provider      TEXT,                 -- 'Netflix', 'Apple TV+', ...
  release_date  TEXT NOT NULL,        -- first date this provider appeared
  notified_at   TEXT,
  UNIQUE(title_id, provider)
);

-- Push subscription (single row in practice; table allows multiple devices).
CREATE TABLE push_subs (
  id            INTEGER PRIMARY KEY,
  endpoint      TEXT NOT NULL UNIQUE,
  p256dh        TEXT NOT NULL,
  auth          TEXT NOT NULL,
  created_at    TEXT NOT NULL
);

-- Cached AI suggestions (regenerated nightly + on manual refresh).
CREATE TABLE suggestions (
  id            INTEGER PRIMARY KEY,
  tmdb_id       INTEGER NOT NULL,
  media_type    TEXT NOT NULL,
  audience      TEXT NOT NULL,        -- suggested list (me/us/family)
  payload       TEXT NOT NULL,        -- JSON {name,poster_path,critic_score,rt_score,reason,meta}
  generated_at  TEXT NOT NULL,
  UNIQUE(tmdb_id, media_type)
);

-- Single-row app settings.
CREATE TABLE settings (
  id                INTEGER PRIMARY KEY CHECK (id = 1),
  critic_threshold  INTEGER NOT NULL DEFAULT 75,   -- 60–95, Discover gate
  soft_prompt_seen  INTEGER NOT NULL DEFAULT 0,    -- shown the pre-permission card?
  updated_at        TEXT NOT NULL
);

CREATE INDEX idx_entries_state       ON entries(state);
CREATE INDEX idx_entries_title       ON entries(title_id);
CREATE INDEX idx_episodes_title      ON episodes(title_id);
CREATE INDEX idx_episodes_air        ON episodes(air_date);
CREATE INDEX idx_episodes_unwatched  ON episodes(title_id, watched_at);
CREATE INDEX idx_releases_title      ON releases(title_id);
CREATE INDEX idx_titles_tmdb         ON titles(tmdb_id, media_type);
```

- **`scripts/seed.ts`** — inserts ~6 titles (matching the mockup's cast so the UI has real palettes to render), a spread of entries across all three audiences and all four states, a couple of seasons of episodes with mixed `watched_at`, and one film `releases` row. ### 2.5 Schema decisions worth flagging

- **`entries UNIQUE(title_id, audience)`** — the mockup shows the same title (Cliffhold, The Quiet Ward) under multiple audiences. One `titles` row, one `entries` row per audience. Progress on `episodes`/`releases` is title-level, shared across audiences (you don't re-watch per audience).
- **`episodes.notified_at` added** — PRD §5 branches on "no `notified_at`" but PRD §3's `episodes` table omitted the column. Added.
- **`ON DELETE CASCADE`** — removing a title cleans up its entries/episodes/releases.

## 3. API surface

All routes are Cloudflare Pages Functions under `/api`, JSON in/out, behind Cloudflare Access. `_middleware.ts` reads `Cf-Access-Authenticated-User-Email`, rejects anything absent with `401`, and wraps handlers so thrown errors become `{ error: { code, message } }`. Success bodies are the raw resource(s). All timestamps ISO 8601 UTC.

**Standard error shape:** `{ "error": { "code": "not_found" | "bad_request" | "upstream" | "rate_limited" | "server", "message": string } }` with matching HTTP status.

| # | Method | Path | Purpose |
|---|--------|------|---------|
| 1 | GET | `/api/search?q=` | TMDB multi-search for the Add sheet |
| 2 | GET | `/api/titles` | Full library (titles + entries + progress rollups) |
| 3 | POST | `/api/titles` | Add a title (TMDB import + palette + critic score + entry) |
| 4 | GET | `/api/titles/:id` | One title with seasons/episodes/releases/entry |
| 5 | PATCH | `/api/titles/:id` | Refresh metadata / re-run enrichment (rare) |
| 6 | DELETE | `/api/titles/:id` | Remove title + its entry (cascade) |
| 7 | PATCH | `/api/entries/:id` | Change `state`, `audience`, or `notify` |
| 8 | POST | `/api/progress` | Mark episode(s) or a film watched — **the fast path** |
| 9 | GET | `/api/calendar?from=&to=` | Upcoming episodes + releases in a window |
| 10 | GET | `/api/suggestions` | Cached suggestions (post-threshold) |
| 11 | POST | `/api/suggestions` | Manual regenerate (Discover refresh) |
| 12 | GET | `/api/settings` | Read settings |
| 13 | PATCH | `/api/settings` | Update critic threshold / flags |
| 14 | GET | `/api/push/vapid-public` | VAPID public key for `subscribe()` |
| 15 | POST | `/api/push/subscribe` | Store a PushSubscription |
| 16 | POST | `/api/push/unsubscribe` | Remove a subscription by endpoint |

### Detail

**1. `GET /api/search?q=`** → `200 { results: SearchResult[] }` where `SearchResult = { tmdb_id, media_type, name, year, poster_path, overview }`. Filters TMDB `multi` results to `movie`/`tv` only, drops person results. `q` empty → `400`. TMDB down → `502 upstream`.

**3. `POST /api/titles`** — body `{ tmdb_id, media_type, audience, state?='saved' }`.
Flow: fetch TMDB detail (`append_to_response=external_ids,watch/providers`) → for TV also fetch season/episode list → extract IMDb id → OMDb critic lookup → `resolveCriticScore` → palette extraction from `w154` poster → insert/upsert `titles`, insert `entries` (unique per audience), bulk-insert `episodes` (TV) / seed `releases` (movie). Returns `201 { title, entry }`. Duplicate audience entry → `409 { error: bad_request }`. Palette/OMDb failures are **non-fatal**: title still added, `critic_score` falls back to TMDB, palette falls back to a neutral oxblood-tinted default.

**4. `GET /api/titles/:id`** → `200 { title, entry, seasons: [{season, episodes:[…]}], releases:[…] }`. Seasons assembled from `episodes` grouped and sorted. `404` if not found.

**7. `PATCH /api/entries/:id`** — body any subset of `{ state, audience, notify }`. Validates enums. On `state` → sets `updated_at`. Returns `200 { entry }`. Changing `audience` respects the unique constraint (`409` if that audience already tracks the title).

**8. `POST /api/progress`** — the notification + tap fast path. Body one of:
- TV single: `{ entryId, titleId, season, episode }`
- TV season: `{ titleId, season, all: true }`
- Film: `{ entryId, titleId }`
Sets `watched_at = now` on the matching episode(s) (idempotent — re-marking is a no-op), or for a film flips the entry to `completed`. Auto-advances TV entry state: if all aired episodes now watched → `completed`, else `watching`. Returns `200 { updated: n, entryState }`. **Designed to be called from the service worker with no window** — tiny body, no auth redirect (Access service token / same-origin cookie carried by the SW fetch). Idempotency means a replayed offline write is safe.

**9. `GET /api/calendar?from=&to=`** → `200 { days: [{ date, items: [{ type:'episode'|'release', title_id, name, label, audience, poster_path }] }] }`. Server buckets episodes (`air_date`) and releases (`release_date`) in `[from,to]` by day.

**10. `GET /api/suggestions`** → `200 { suggestions: Suggestion[], generated_at }` where each `Suggestion = { tmdb_id, media_type, audience, name, poster_path, rt_score, critic_score, reason, meta }`, pre-filtered to `critic_score >= settings.critic_threshold`, capped at 8. Empty cache → `{ suggestions: [], generated_at: null }`.

**11. `POST /api/suggestions`** → runs the Haiku pipeline (§7) synchronously (budgeted ~a few s), rewrites the `suggestions` cache, returns the same shape as #10. Concurrency-guarded so a double-tap doesn't run it twice.

**13. `PATCH /api/settings`** — body subset of `{ critic_threshold (60–95), soft_prompt_seen }`. Clamps threshold to range. Returns `200 { settings }`.

**14–16 push** — see §6.

## 4. TMDB integration

Base `https://api.themoviedb.org/3`. Auth via **v4 read token** in `Authorization: Bearer` (cleaner than `api_key` query). `TMDB_TOKEN` is a secret. Client lives in `shared/tmdb.ts`, imported by Functions and the Worker only — **never** the browser.

### 4.1 Endpoints used

| Surface | Endpoint | Params |
|---|---|---|
| Add-sheet search | `GET /search/multi` | `query`, `include_adult=false`, `language=en-US` |
| Add / detail (movie) | `GET /movie/{id}` | `append_to_response=external_ids,watch/providers,release_dates` |
| Add / detail (tv) | `GET /tv/{id}` | `append_to_response=external_ids,watch/providers` |
| TV episodes | `GET /tv/{id}/season/{n}` | per season, for `episodes` rows |
| Streaming (cron) | `GET /movie/{id}/watch/providers` · `/tv/{id}/watch/providers` | region read as `results.IE` |
| Discover candidates | `GET /discover/movie` · `/discover/tv` | `watch_region=IE`, `sort_by`, genre/decade filters from taste profile |
| Recommendations | `GET /movie/{id}/recommendations` · `/tv/{id}/recommendations` | seeded from finished titles |

### 4.2 Region handling (IE)

- **Watch providers:** always read the `IE` key from `watch/providers.results`; a title with no IE availability has no release to notify on (skip). Prefer `flatrate` (subscription) providers; `rent`/`buy` ignored for notifications (PRD is about "arriving on streaming").
- **Discover:** `watch_region=IE` + `with_watch_monetization_types=flatrate` so candidates are actually watchable here.
- **Language:** `en-US` for text (TMDB's most complete metadata), region `IE` only for availability/dates. Release dates for films read from `release_dates.results.IE` when present, else the global `release_date`.

### 4.3 Image sizes per surface

Helper `img(path, size)` → `https://image.tmdb.org/t/p/{size}{path}`.

| Surface | Size | Aspect |
|---|---|---|
| Palette extraction (server) | `w154` | poster |
| Saved grid, suggestion card, add-sheet result | `w342` | 3:4 |
| Keep-Going rail | `w500` (backdrop) | 16:10 |
| Hero carousel | `w780` | 4:5 |
| Title-detail full-bleed header | `w1280` (backdrop) | — |

Every image sits in a container with a fixed `aspect-ratio` (zero layout shift, PRD §11). `PosterImage` sets `loading="lazy"` below the fold, `decoding="async"`, `width`/`height` attributes, and a palette-derived solid background as the placeholder (blur-up optional).

### 4.4 Palette extraction (server-side only, PRD non-negotiable)

`shared/palette.ts`: fetch `w154` poster → decode with **`jpeg-js`** (pure JS, runs in Workers, no canvas) → downsample to ~40×60 → **median-cut** quantise to a small set → pick 4 dominant colours by weight → map to the shape the mockup's `Art`/`Ambience` already consume:

```json
{ "base": "#0A2530", "a": "#4FD1C5", "b": "#0E5E7A", "c": "#BCF3EA", "tint": "#7FD8D0" }
```

Mapping rule: `base` = darkest cluster (the artwork ground), `a` = most saturated (the hero glow), `b` = second most saturated, `c` = lightest, `tint` = `a` lightened ~18% (the ambient field). Stored as JSON in `titles.art_palette` at add-time. If decode/fetch fails, store a neutral fallback derived from oxblood so the UI never breaks. **No client-side canvas, ever.**

### 4.5 Rate limits & caching

- TMDB allows ~50 req/s — generous. The real cost is the nightly cron and detail imports, both server-side.
- **Cache everything durable in D1.** Metadata, episodes, palette, genres are written once at add-time and only refreshed on explicit `PATCH /api/titles/:id`.
- The cron's per-title provider/season polls are the recurring cost: for a personal library (tens of titles) this is trivially under any limit. Cron fetches sequentially with a small concurrency cap (e.g. 4) and a soft per-run budget.
- Poster bytes are served straight from TMDB's CDN to the browser; R2 caching is explicitly deferred (PRD §10 "optional").

## 5. Critic scores (Rotten Tomatoes / OMDb) — implementation

Resolved in §0.1. Implementation contract:

- **`shared/omdb.ts`** — `getRottenTomatoes(imdbId): Promise<number | null>`. `GET https://www.omdbapi.com/?i={imdbId}&apikey={OMDB_KEY}`. Parse `Ratings[]` for `Source === "Rotten Tomatoes"`; `"94%"` → `94`. Missing / `N/A` / non-200 → `null`. `OMDB_KEY` is a secret.
- **`shared/critic.ts`** — `resolveCriticScore({ rt, tmdbVote, mediaType }): { rt_score: number|null, critic_score: number }`.
  - `rt_score = rt` (may be null).
  - `critic_score = rt ?? Math.round(tmdbVote * 10)` (tmdbVote 0–10 → 0–100). If both absent, `critic_score = 0` (won't clear any threshold — correctly hidden from Discover).
- **When called:** at `POST /api/titles` (add-time) and during the nightly suggestion enrichment for candidates. `rt_checked_at` throttles re-checks to at most once per 14 days per title, keeping OMDb calls far under the 1,000/day cap.
- **UI:** `ScoreBadge` shows `rt_score` with the RT-style red dot when non-null; otherwise `critic_score` with a neutral dot and no "RT" implication. Slider label reads **"Critic score floor"** (matches mockup).

## 6. Push notifications

### 6.1 VAPID keys — generation & storage

- Generate once: `npx web-push generate-vapid-keys` → a public/private pair.
- **Public key** → non-secret; exposed via `GET /api/push/vapid-public` and used by the browser in `pushManager.subscribe({ applicationServerKey })`.
- **Private key** → secret, set in **both** the Pages project and the Worker (`wrangler secret put VAPID_PRIVATE_KEY`), because both may send (Functions never send in v1, but the Worker does nightly; keep symmetric for future).
- `VAPID_SUBJECT` = `mailto:` contact, also a var.
- Signing uses **Web Crypto** (`@block65/webcrypto-web-push` or an equivalent Workers-compatible sender) in `shared/push-send.ts`. The Node `web-push` library is **not** Workers-compatible and is used only for the one-off key generation.

### 6.2 Service worker registration flow

1. `main.tsx` registers `sw.ts` (built by `vite-plugin-pwa` `injectManifest`) on load — this only enables offline + push handling, it does **not** ask for permission.
2. Permission is never requested on first load (PRD §5). The **first time a title is added**, if `Notification.permission === 'default'` and `settings.soft_prompt_seen` is false, show `SoftPushPrompt` (in-app card explaining the one job: "Pict will tell you the moment something you're tracking is out").
3. Only on the card's "Turn on" does `usePush.subscribe()` call `Notification.requestPermission()`, then `registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })`, then `POST /api/push/subscribe`. Set `soft_prompt_seen = 1` regardless of outcome so it never nags.

### 6.3 Subscription lifecycle

- **Store:** `POST /api/push/subscribe` upserts `{ endpoint, p256dh, auth }` (unique on endpoint).
- **Refresh:** `pushsubscriptionchange` in the SW re-subscribes and re-posts.
- **Expiry / 404 / 410 on send:** the sender deletes that `push_subs` row (dead endpoint).
- **Unsubscribe:** Settings toggle → `pushManager.getSubscription().unsubscribe()` + `POST /api/push/unsubscribe {endpoint}`.

### 6.4 Cron worker — exact daily logic

`worker/src/index.ts` `scheduled()` runs (see timezone guard in §1). Steps:

1. **Guard:** compute Europe/Dublin hour; `return` unless `08`. Then `if (withinQuietHours(now)) return;` — the v1 stub returns `false` (see §0.3).
2. **Collect notifiable entries:** `entries` where `state IN ('saved','watching')` and `notify = 1`, joined to `titles`.
3. **TV** — for each TV title: ensure `episodes` are fresh (fetch any seasons updated since last check), then find episodes with `air_date == today` (Europe/Dublin) and `notified_at IS NULL`. Each → a queued push `{ kind:'tv', entryId, titleId, season, number, name, titleName }`.
4. **Film** — for each movie title: `GET watch/providers` region IE. For any `flatrate` provider not already in `releases` for this title → insert `releases` row (`release_date = today`, `notified_at = NULL`) → queue `{ kind:'film', entryId, titleId, provider, titleName }`.
5. **Batch rule:** if a single run queues **more than three** items total → collapse into one batched push `"3 new episodes are out today"` (or a mixed "N new titles are out today"). Otherwise send each individually.
6. **Send** via `shared/push-send.ts` to every `push_subs` row.
7. **Mark:** set `notified_at = now` on each episode/release actually notified (batched or not) so nothing double-fires. Dead endpoints pruned.
8. **Nightly suggestions:** after the notify sweep, run the Haiku pipeline (§7) and overwrite the `suggestions` cache.

### 6.5 De-duplication rules

- `episodes.notified_at` and `releases.notified_at` are the single source of truth — an item is notified at most once, ever.
- `releases UNIQUE(title_id, provider)` ensures a provider appearing again doesn't re-fire.
- Batching still writes `notified_at` on every collapsed item (§6.4.7).
- Cron is idempotent within a day: a re-run finds everything already marked and queues nothing.

### 6.6 Notification action buttons (PRD §5) — the fast path

**Payload** on every actionable notification:
```json
{
  "title": "Cliffhold — Season 3, Episode 1 is out",
  "options": {
    "body": "Apple TV+ · Us Two",
    "tag": "ep-1234",
    "data": { "kind": "tv", "entryId": 12, "titleId": 34, "season": 3, "episode": 1, "deepLink": "/title/34" },
    "actions": [ { "action": "watched", "title": "Mark watched" },
                 { "action": "snooze",  "title": "Snooze" } ]
  }
}
```

| Notification | Actions | Notes |
|---|---|---|
| TV episode released | `Mark watched` · `Snooze` | exactly two — Android Chrome max |
| Film now streaming | `Mark watched` · `Not yet` | |
| Batched (3+) | *(none)* — body-tap opens Pict | too ambiguous to act on in place |

**`notificationclick` handler (in `sw.ts`), branching on `event.action`:**

- **`watched`** → build the `/api/progress` body from `event.notification.data` → `fetch('/api/progress', {POST})`. On success `event.notification.close()` and show the confirmation notification. **Never `clients.openWindow()`** for this action. If `fetch` throws (offline) → push the write onto the **same IndexedDB sync queue** the app shell uses (§10) and register a `sync` tag; still show the confirmation optimistically. `event.waitUntil()` wraps all of it.
- **`snooze`** → `event.notification.close()`, and schedule the identical notification ~24h later. Implementation: write a `snoozed` record to IDB with a `fireAfter` timestamp; the next cron run (or a `showNotification` on next SW wake past `fireAfter`) re-displays it. No server write.
- **`not-yet`** (film) → just `event.notification.close()`. No write.
- **default (body tap / batched)** → focus an existing Pict client or `openWindow(data.deepLink ?? '/')`.

**Confirmation notification** after a successful/queued `watched` write:
```
Marked watched — Cliffhold S3E1
```
`{ tag: 'confirm-<epId>', silent: true, requireInteraction: false, actions: [] }`, and the SW sets a timer to `getNotifications({tag})` and `.close()` after ~4s. Silent, no vibration (PRD §5).

**Constraint honoured:** never more than two `actions` declared; `watched` never opens a window.

## 7. AI suggestions (Claude Haiku)

Model: **`claude-haiku-4-5-20251001`** via the Anthropic API (Worker binding / `ANTHROPIC_API_KEY` secret). Pipeline in `shared/haiku.ts`, run nightly by the cron and by `POST /api/suggestions`.

### 7.1 Pipeline

1. **Taste profile** from *eligible* titles (§0.2): film `state='completed'`; TV `state='completed'` **or** (`state='watching'` **and** no aired-but-unwatched episodes). Aggregate genres, decades, avg runtime, networks, and the audience each came from. **Abandoned excluded.**
2. **Candidates** — TMDB `/discover` (seeded by top genres/decades, `watch_region=IE`, flatrate) + `/recommendations` from finished titles. Exclude anything already in `titles` **and** anything ever marked `abandoned`.
3. **Enrich** each candidate with `critic_score` (§5). **Hard-filter** below `settings.critic_threshold` *before* calling Haiku (so Haiku only ever ranks eligible titles and can't resurrect a low scorer).
4. **Haiku call** — send profile + filtered candidates (capped ~30 to bound tokens), ask for the **top 8** with a one-sentence grounded reason each.
5. **Parse & validate** against the zod schema (§7.3). Tag each with a suggested audience from its source titles. Write to `suggestions` cache.

### 7.2 The prompt

**System:**
```
You are the recommendation engine for Pict, a personal TV-and-film tracker for one user in Ireland.
You will be given the user's taste profile (built only from titles they have FINISHED or are fully caught up on) and a list of candidate titles that have already passed a critic-score filter.
Choose the 8 best candidates for this user and, for each, write one short reason.

Hard rules:
- Choose ONLY from the provided candidates. Never invent a title or use one not in the list.
- Every reason MUST name a specific title the user finished — e.g. "Because you finished Cliffhold" — never vague genre talk like "because you like drama".
- Each reason is at most 90 characters, renders on one line, warm and plain, no marketing tone.
- Pick a suggested audience for each from {me, us, family}, based on which lists its most-similar finished titles came from.
- Return JSON ONLY, matching the given schema. No prose, no markdown, no code fences.
```

**User (JSON):**
```json
{
  "profile": {
    "finished": [{ "name": "Cliffhold", "genres": ["Drama","Thriller"], "decade": "2020s", "audience": "us" }],
    "genres_top": ["Drama","Thriller","Sci-Fi"],
    "decades_top": ["2020s","2010s"],
    "avg_runtime_min": 52,
    "networks_top": ["Apple TV+","Netflix"]
  },
  "candidates": [
    { "tmdb_id": 555, "media_type": "movie", "name": "The Salt Road", "genres": ["Drama"], "year": 2025, "critic_score": 94, "runtime_min": 124 }
  ],
  "count": 8
}
```

### 7.3 Required JSON schema (zod in `shared/schema.ts`)

```ts
const Suggestion = z.object({
  tmdb_id:    z.number().int(),
  media_type: z.enum(["movie", "tv"]),
  audience:   z.enum(["me", "us", "family"]),
  reason:     z.string().min(1).max(90),
});
const HaikuResponse = z.object({ suggestions: z.array(Suggestion).min(1).max(8) });
```

Request `response_format`-style discipline via the prompt; also pass a low `max_tokens` and `temperature ~0.4`.

### 7.4 Validation & fallback

- Strip any accidental code fences / leading prose before `JSON.parse`.
- Parse → `HaikuResponse.safeParse`. On failure: **one** retry with an appended "Your previous reply was invalid JSON. Return only the JSON object." On second failure → **fallback**: skip Haiku entirely and build suggestions deterministically — take the top-8 filtered candidates sorted by `critic_score` desc, and synthesise reasons of the form `"Similar to {closest finished title}"` computed by genre overlap. The Discover tab **always renders**; it never shows an error because the model misbehaved.
- Drop any returned `tmdb_id` not in the candidate set (anti-hallucination), backfill from the sorted fallback list to keep 8.
- Truncate any reason >90 chars at a word boundary.
- Re-hydrate each suggestion with `name/poster_path/critic_score/rt_score/meta` from the candidate record (never trust the model for those) before caching.

## 10. Offline strategy

- **App shell** — precached by `vite-plugin-pwa` (`injectManifest`): HTML, JS, CSS, fonts, icons. Installable, launches offline.
- **Library data** — `GET /api/titles`, `/api/settings`, `/api/calendar`, `/api/suggestions` are cached in **IndexedDB** (`src/lib/idb.ts`, via the `idb` package). `useLibrary` renders from IDB **instantly**, then revalidates from the network and diffs in (PRD §11: "renders from IndexedDB cache instantly, then revalidates").
- **Poster images** — runtime `CacheFirst` (`vite-plugin-pwa` `runtimeCaching`) for `image.tmdb.org`, capped (e.g. 300 entries / 30 days).
- **Writes while offline** — the **sync queue**. `POST /api/progress` and `PATCH /api/entries/:id` are the only offline-write paths. When offline (or from the SW notification handler), the mutation is appended to an IDB `sync-queue` store as `{ id, url, method, body, ts }`, and the UI updates optimistically. On `online` / Background Sync `sync` event / next app open, `src/lib/sync.ts` replays them FIFO and clears on success.
- **Conflict resolution** — writes are **idempotent and last-write-wins by design**: `watched_at` is a set-to-timestamp (re-marking is a no-op), `state`/`notify`/`audience` are absolute assignments carrying the client `ts`. The server applies them unconditionally; a replayed or duplicated write converges to the same state. No merge logic needed because there is a single user and no field is incrementally mutated.
- **The notification `watched` write uses this same queue** (PRD §5) — the SW imports the same IDB helper, so a mark-watched fired offline from the notification shade replays exactly like an in-app one.

## Judgement calls you might disagree with

1. **Unified `critic_score` column, "Critic score" naming (kept, not replaced).** OMDb *does* still return RT, so I didn't fully switch to `vote_average` — but RT coverage is too thin for TV/Irish content to gate on alone, so I store a resolved `critic_score` that prefers RT and falls back to TMDB, and named the setting "Critic score". If you'd rather the badge *only* ever show a real RT number (and hide the badge otherwise), that's a one-line change in `ScoreBadge`.
2. **`entries UNIQUE(title_id, audience)` — one title, many audiences.** The mockup shows the same show under two audiences; I modelled that as multiple entries over one shared title with shared episode progress. If "Us Two" and "Family" should track progress *independently* on the same show, progress would need to move to `entries` and this gets more complex. I assumed shared.
3. **Two cron expressions + in-handler hour check for the DST-correct 08:00.** Slightly ugly but the only reliable way to hit local 08:00 year-round with UTC cron. The alternative (accepting 08:00 UTC = 09:00 in summer) is simpler if you don't mind the drift.
4. **`jpeg-js` + median-cut for server palette extraction.** Workers have no canvas; this is a pure-JS decode of a tiny `w154` poster. It's the pragmatic choice, but if palettes look muddy we can switch to Cloudflare Images or precompute from TMDB's `backdrop` instead.
5. **Snooze implemented client-side (IDB + re-show), not server-scheduled.** Web Push can't self-schedule a future notification without a server tick; I piggyback on the daily cron / next SW wake rather than adding a queue table. Snoozes therefore resolve at the next cron, not exactly 24h to the minute. Acceptable for a personal app; flag if you want minute-accurate snooze.
6. **Discover hard-filters *before* Haiku.** The model never sees sub-threshold candidates, so it can't argue one back in. Cleaner, but it means Haiku can't say "this 72% is worth breaking your rule for." Intentional — the threshold is a gate, not a suggestion.

## PRD gaps / contradictions found

- **`episodes.notified_at` missing.** PRD §5 branches on it; PRD §3's DDL omits it. **Added.**
- **No `settings` table** despite a user-adjustable critic threshold and a soft-prompt-seen flag. **Added** (single row).
- **No `imdb_id` on `titles`**, yet reliable OMDb lookups need it. **Added** (from TMDB `external_ids`).
- **Taste-profile fields not stored.** §6 needs genres/decades/runtime/networks; §3's `titles` had none. **Added** `genres`, `networks`, `runtime`, `tmdb_vote`.
- **"Batched if more than three" vs copy "3 new episodes".** ">3" means the batch triggers at 4+, but the sample copy says "3". Treated the **count as illustrative**; batch fires at **>3** (4+) per §5, copy interpolates the real number.
- **Cron timezone.** PRD says "08:00 Europe/Dublin"; Cloudflare cron is UTC-only. Resolved with the dual-expression + hour-guard approach.
- **`suggestions` audience.** §6 says suggestions carry an audience tag; §3's table had no column. **Added** `audience`.
- **Auth for the SW `POST /api/progress`.** Cloudflare Access fronts everything; a background `fetch` from the SW must carry the Access session cookie (same-origin, it will) or a service token.
